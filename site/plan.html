    一、素材一：morphicons（图标变形）

    项 内容
    素材形态 社交平台图文卡片，作者 guillermo0g
    它是什么 任意 stroke 图标可互相变形的图标库：只改一个 prop，两个图标之间自动补间
    技术路线 对两个形状求最优 2D 相似变换（Procrustes），在极坐标空间插值；旋转是"涌现"的（arrow-right → arrow-down 自动 90°、plus → x 自动 45°），无需手写配对与旋转组
    支持源 Lucide、Tabler、Heroicons（outline）、Iconoir、shadcn 图标注册表；前提是同一网格（都是 24×24）的 stroke 图标
    三种模式 非受控（改 prop 即变）、受控（from/to + progress，用于手势与滚动）、命令式（ref.morphTo()）
    工程细节 SSR 输出静态 SVG 无水合闪烁；打断时从当前中间形状重规划并保留弹簧速度；全页共用一个 rAF；prefers-reduced-motion 降级为瞬时切换
    与 Cinder 的关系 Cinder 图标库已是 Lucide 104 个、24×24 stroke，正好满足它的网格前提

    1.1 冲突与吸收边界

    Cinder 纪律 冲突点 结论
    零依赖、删除 JS 退化 变形必须有运行时（Procrustes + 插值 + rAF） 只做可选行为层，不跑就静态切换
    图标以 mask + .cin-i-* 类名引用 mask 无法插值路径 变形只作用于内联 <svg> 场景；mask 路径保留给普通图标
    单入口 8KB 插值算法约 3–5KB 独立入口 dist/js/icon-morph.js，不进 base 主包

    1.2 分档（两档都做，但分先后）

    • M1 交叉淡化（必做）：.cin-icon-stack 双层图标叠加，状态切换时 opacity + 轻微 rotate/scale 交叉，纯 CSS，任何图标对都能用。这是"变形"在 Cinder 纪律下的默认形态。
    • M2 真路径插值（可选）：initIconMorph() 读 dist/cinder-icons.svg 的 path，做极坐标插值。仅在需要"一个图标真的长成另一个"时引入。

    3.1 为什么这件素材对 Cinder 比前两件更重要

    前两件是"好看"（玻璃质感）与"好拼"（AI 组件）。这一件是**"会说话"**：它把"助手此刻在干什么"变成一套可枚举的状态语汇——39 个状态分四族（生命周期 sleeping/waking/idle/listening/thinking/searching/working；情绪反应 excited/confused/sad/celebrate…；Agent 型 orbit/radar/progress；产品动作 spawning/loading/dictating/sending/uploading/alerting…）。

    Cinder 现在有 thinking、task-rows、stream-text、notice-bar，各自都在描述 Agent 状态，但没有一份统一的状态表——这导致三个组件对"failed"的表达各写各的。这是真正的缺口，且零代码即可先补。

    4.1 关键判断：29 个里混着三类完全不同的东西

    这是本批最重要的结论——不能整体吸收，也不能整体拒绝：

    类别 个例 判定
    A 装饰动效（好看，但会喧宾夺主） ShinyButton、ChromeButton、DitherButton、GlitchButton、HighlightButton、FrameButton、AquaButton、ConfettiButton 收 4 个（shiny / chrome / dither / glitch），其余不做
    B 防误触闸门（真价值） HoldButton、SlideToDetonate、CooldownButton、MorphStatusButton、RevealButton 全收，是本批核心产出
    C 黑暗模式（恶意设计） TrollButton（躲光标）、DoubtButton（连环内疚确认）、CooldownButton 的嘲讽文案、ClickPowerUp 的蓄能惩罚 全拒，进 D 档
    D 技术不可移植 ThrusterButton（WebGL 烟雾）、DemonicButton（Canvas 火焰）、AshBurstButton（Matter.js 物理）、MinecraftButton（碎块物理）、MoviePassButton（撕票铰链） 拒，理由见 D 档
    E 只是基样式，不是动效 MinimalButton、BrutalButton、ThreeDButton、RealisticSwitch、CommandButton ThreeD 的按压物理感与 Command 的键帽可视化收；其余已覆盖或不收

    合计 8 + 5 + 4 + 7 + 5 = 29，全覆盖。

    4.2 为什么 B 类才是真价值

    approval-card 解决的是**"要不要做"（决策闸门：风险分级、批准/拒绝）；B 类解决的是"确认真的要做"**（动作闸门：物理代价）。两者互补而非重复：

    • HoldButton：按住 0→100%，提前松手抖动中止——比二次弹窗更防误触，且不打断流程；
    • SlideToDetonate：滑动解锁，移动端拇指误触几乎为零；
    • CooldownButton：径向冷却 + 防连点，直接干掉重复提交；
    • MorphStatusButton：同一按钮原地穿过 idle/loading/success/error，无布局位移——这是提交按钮的标准难题；
    • RevealButton：按住揭示敏感值，替代"明文常驻"。

    近语的直接用例：清空对话、删除本地模型、覆盖文件、卸载扩展——四个破坏性动作都该用 hold 或 slide，而不是一个轻飘飘的确认框。

    4.3 黑暗模式判定标准（三条，可判定、可写进 review）

    一个交互只要命中任一条，就不进库：

    1. 故意延迟或阻碍用户已明确表达的意图（TrollButton 让按钮逃跑）；
    2. 用羞辱、内疚、嘲讽话术施压（DoubtButton 的连环自省式确认）；
    3. 让"取消"比"确认"更费劲（成本不对称：确认一键、取消要翻三层）。

    这三条也反向约束我们自己：确认闸门的强度必须与后果严重程度成正比，普通操作不许加 hold ——否则我们就在制造慢速的黑暗模式。

    4.4 动效硬约束（本批新增，写进 docs/motion-rules.md）

    1. 时长：按压反馈 ≤120ms，状态切换 ≤240ms；除背景常驻类外不允许 >1s 的循环动画；
    2. 动效不得推迟可点击时间（TrollButton 的反面教材）；
    3. prefers-reduced-motion 下全部静止，且静止态必须仍表达完整信息（不能靠动画传达"处理中"）；
    4. 禁止为动效引入位图、WebGL、物理引擎；
    5. 单屏装饰性动效 ≤2 处；主操作按钮默认无装饰动效。

    5.1 图1 的核心论点（Rive / 多邻国）

    论点 原文要点 对 Cinder 的意义
    动画 ≠ 行为 "动画做好了，但用户什么时候触发它？操作中断了怎么办？成功、失败之后又该是什么动作" 组件契约必须能回答这四问，否则只算样式
    身体与表情分离 多邻国：角色身体动态与嘴型分别控制，再按事件组合 形象层必须双轴（状态 × 表情），不能压成一张大表
    事件驱动 图形、动画、切换逻辑在同一工作流，数据变化改变元素 Cinder 用 data-state + CSS 承载静态可达的部分，复杂联动明确外挂
    工具边界 AE 难胜任复杂交互；Lottie 适合单条线性动画；多状态 / 频繁交互 / 数据驱动才需要 Rive 反向定义能力边界：超出即外挂，不塞进 CSS 库
    入门路径 先把按钮 default / pressed / success / failure 四态跑通，再上角色 与 G8 的 T35 同向，T35 扩容为五态（补中断）

    结论：Cinder 收"动效行为契约"，不收动效运行时。Rive / Lottie 的价值不在代码，在"每个组件必须写明四问答案"这条约束。

    5.2 图2 的核心参数（beUI）

    beUI：React 动效组件库，Framer Motion + Tailwind，遵循 shadcn-ui 目录约定（@beui 命名空间），124 组件，MIT，React 18，每个组件配参数可调演示与旁白视频，设计原则直接写在组件里。

    它比前几批素材更硬的地方是给了可判定的量化值：

    参数 原始表述 采纳
    页面级动效时长 动效动画不超过 300ms 采纳，与 T33 的"按压 ≤120ms / 状态 ≤240ms"合并成一张表
    同一动效频次 一页最多出现一次 采纳（原文表述含混，只取可执行部分：同屏同类动效不重复）

    七、通用层与定制层的关系（为什么 G6/G7 排在玻璃之后但优先级不低）

    Cinder 是通用组件库，thinking / tool-chips / approval-card / stream-text 属于与业务无关的 AI 交互通用件，任何带有 AI 会话的产品都能直接用；G6 补的 task-rows（长任务执行态）与 prompt-bar（输入器）是这类界面普遍缺的两块。G7 同理：任何带语音入口的产品都需要"会听、会想、会回应"的状态语汇，listening / thinking / streaming 三态是可复用的通用抽象。

    这三批能力都留在 base 通用层，不写进任何定制层；确需业务语义时，只在定制层包一层壳，不下沉进 base。

    玻璃层是质感增强，G6 是功能缺口，G7 是产品辨识度——若时间紧，可把 G6 提到 G2 之前，G7 与 G3 并行（G7 只碰新文件与 data-state 别名，与玻璃层的容器选择器改动不冲突）。
