    贡献指南

    改动流程、构建闸门与提交纪律

    面向人的上手路径。仓库硬约定以 AGENTS.md 为准（AI Agent 与人共用同一套约束），本文件只回答"第一次来怎么跑起来、改什么、怎么算改完"。

    1. 五分钟跑起来

    bash scripts/selfcheck.sh     # 环境自检（11 项）；沙箱/新机器第一次必跑
node build.mjs                # 构建 dist 与 60 个按需入口
node build.mjs --check        # 校验：0 error 是底线
npm run acceptance            # 52 组验收全跑（playwright 无头 chromium）

    三条命令的判定口径：

    • build --check 出现任何 error 即视为未完成，不接受"先提交后修"。
    • acceptance 出现新的 FAIL 即回退改动；不允许把断言改成 PASS 来消错。
    • XFAIL 只减不增；新增 XFAIL 必须同时在 docs/known-issues.md 登记 KN 编号。

    按组件单跑：node scripts/acceptance-all.mjs tabs（名称模糊匹配）。

    2. 仓库里有什么

    目录 内容 是否进发布包
    packages/base/src/components/ 60 个通用组件（一组件一 .css） 是（编译后）
    packages/base/src/intents/ 60 份意图契约（与组件同名 .md，四段硬约束） 否
    packages/base/src/behaviors/ 34 个行为层 JS（渐进增强，挂 window.Cinder） 是（编译后）
    packages/base/src/primitives/ 12 个 JS 原语（focus / gesture / presence / stream / undo / i18n 等） 是（编译后）
    packages/erp/src/blocks/ 6 个 ERP 业务块（PDA、审批、明细行、选择器、打印、单据） 是（编译后）
    demos/ 44 个可跑演示页 否
    scripts/ 52 个验收脚本 + 自检 否
    docs/ 契约模板、已知缺陷、对标矩阵、可访问性声明 否

    设计原则：去中心化自包含——每个组件独立 CSS（可选 JS），可单文件拷贝，无中心注册表、无强制构建链；删掉 JS 退回语义标签仍可用。

    3. 改什么：先过"四族 × 五档"

    四族：基础件 / 组合件 / 场景件 / 容器件；五档：A 立即补 / B 排期补 / C 软线 / D 不做 / E 已有覆盖。

    判定顺序不许跳步：

    1. 先查存量 —— ls packages/base/src/components、ls packages/base/src/intents。能拼出来就不新增（多数需求是组合问题，不是缺组件）。
    2. 再判档位 —— 确有缺口，定族定档；C / D 档必须先写出替代方案。
    3. 只有 A / B 档才动手。

    4. 算改完的标准

    4.1 改样式 / 改状态

    • 只动一个主题，不夹带格式化、重命名、顺手微调。
    • 颜色、间距、圆角、字号一律走 --cin-* 令牌，禁止裸十六进制色值与 !important。
    • 方位属性一律用逻辑属性：margin-inline-start / padding-inline / text-align: start|end，禁止 left / right；必须镜像的图形用 :dir(rtl) 显式覆盖。node scripts/acceptance-rtl.mjs 会挡住物理属性。

    4.2 新增组件（缺一不可）

    步骤 产出
    1 packages/base/src/components/<name>.css
    2 packages/base/src/intents/<name>.md —— 四段：边界（负责 / 明确不负责 + 承接方）、状态机与失败态、可访问性、AI 选型提示
    3 有交互则加 src/behaviors/<name>.js，并在 build.mjs 的 JS_DOMAINS 登记所属域
    4 scripts/acceptance-<name>.mjs（acceptance-all.mjs 自动收录）
    5 demos/<name>.html 一页可跑示例
    6 预算变化写清：涨了多少、是否触发冻结阀

    intents 的边界段必须写实，不允许占位骨架；TODO 只能出现在后三段。

    4.3 修 bug

    先补一条会失败的断言，再改代码，断言转 PASS 才算修完。修复后把 KN 条目移入 docs/known-issues.md 文末"已修复"表，保留一行历史。

    5. 预算纪律

    • 入口 gzip ≥7KB，逐字节冻结：涨 1B 即构建失败。先想优化，确需抬高走 node build.mjs --update-baseline，并逐行 review budget-baseline.json 的 diff。
    • 入口 gzip <7KB：按 5% 预警（warning，不阻断）。
    • 禁止调大阈值函数、关闭冻结阀、或改入口名绕过统计。
    • 现状：71 个入口，最重 base/overlay 7628B；全量合订 gzip 140,880B（约 137.6KB）（参考线，不阻断，真实接入走 entries/）。

    视觉基线纪律

    • visual:check 失败先看 tests/visual/diff/<页名>.diff.png，判断是预期改动还是意外回归。
    • 确认预期改动才 npm run visual 覆盖基线，并在同一次提交说明改了哪几页、为什么。
    • 禁止在失败状态下顺手更新基线——那等于把回归洗白，与预算基线的「禁止调大阈值」同源。
    • 新增演示页必须同时补基线，否则 --check 报缺基线。

    文档站纪律

    • 改了 README.md、docs/*.md、CHANGELOG.md 的正文，或改了 dist/cinder-manifest.json，必须重跑 npm run docs，否则 docs:check 会在提交前失败。
    • 禁止手改 site/ 下的产物：它是生成物，手改的部分下次构建就丢。要改样式改 scripts/build-docs.mjs 里的 SITE_CSS，要改页面清单改 PAGES。
    • 新增文档页只做两件事：写 markdown，往 PAGES 加一行（slug / src / title / group）。
    • 站点不引外部字体、CDN 脚本或图标服务；验收里有一条"每页零外域请求"，加了就会被拦。

    6. 需求节奏（与产品方约定）

    "做 XX 库 / XX 系统"类需求默认走：联网调研 → 方案文档 → 列决策点 → 待确认 → 执行。未确认前不落业务代码。

    7. 提交

    • 一个主题一个 commit；dist/ 永不入库。
    • 提交前跑完第 1 节的三条命令。
    • 版本发布：更新 package.json 的 version 与 CHANGELOG.md，二者必须同步。 （内容由AI生成，仅供参考）
