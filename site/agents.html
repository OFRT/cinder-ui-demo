    0. 定位硬约定（新增组件前先看这一条）

    约定 含义 反例
    Cinder 是通用组件库 主体为 CSS + JS，面向任意项目接入，不绑定、不服务于某个具体产品 文档里写"某产品要用的才做"
    分通用层 + 定向定制层 base 只放与业务无关的组件；erp 是在 base 之上按 ERP 方向展开的定制层 把金额、单据状态等业务语义写进 base
    定制层可继续增加 erp 只是当前唯一的定制方向，未来会有其它方向；新增方向按 packages/<方向>/ 平级新增，不改 base 把新方向塞进 erp
    依赖单向 定制层 → base 永不可逆；定制层之间互不依赖 base 引用 erp 令牌
    命名与文案 通用层用中性词；业务词只出现在定制层与演示数据里 base 类名带"进销存/发票"

    1. 三条必跑命令

    bash scripts/selfcheck.sh          # 开工前：环境是否被沙箱重置（11 项）
node build.mjs --check             # 每次改完：0 error 是底线，1 条 warning 是已知合订体积参考线
npm run acceptance                 # 交付前：52 组验收一条命令跑全（含 p0），0 项 XFAIL

    判定口径：

    • build --check 出 任何 error 即视为未完成，不得以"先提交再修"绕过。
    • acceptance 出现新的 FAIL 即回退改动，不得把断言改成 PASS 来消错（除非同时改 docs/known-issues.md 并说明理由）。
    • XFAIL 只能减少不能增加；新增 XFAIL 必须同时登记 KN 编号。

    3. 新增任何东西前先过"四族 × 五档"

    四族：基础件（原子控件）/ 组合件（多原子拼装）/ 场景件（业务语义）/ 容器件（布局与骨架）。 五档：A 立即补 / B 排期补 / C 软线（有替代方案就不补）/ D 不做 / E 已有实现覆盖。

    判定顺序（不许跳步）：

    1. 先查存量：ls packages/base/src 与 packages/base/src/intents，能拼出来就不新增（多数需求是组合件问题，不是缺组件）。
    2. 再查覆盖：确有缺口，判断它属于哪一族哪一档；C/D 档必须先写出替代方案。
    3. 只有 A/B 档才动手，并一次性做完下面这份清单（少一项都算欠账）。

    新增组件的完成清单（缺一不可）

    步骤 产出 校验方式
    1 packages/base/src/<name>.css build --check 能算出该入口字节数
    2 packages/base/src/intents/<name>.md（四段：边界 / 状态机与失败态 / 可访问性 / AI 选型提示） 缺文件 → R5 直接 error
    3 若有交互：src/behaviors/<name>.js，挂 window.Cinder，用 dataset.cinReady 防重入；同时在 build.mjs 的 JS_DOMAINS 里登记所属域 重复初始化不叠加监听；漏登记 → build --check 直接 error
    4 scripts/acceptance-<name>.mjs 并被 acceptance-all.mjs 收录 npm run acceptance 计数 +1
    5 demos/ 一页可跑示例 手工打开无控制台报错
    6 预算变化写清（涨了多少、是否触发冻结） budget-baseline.json 只在不该冻结时才更新

    intents 严禁"占位式补齐"：骨架必须把边界段写实（负责 / 明确不负责 + 承接方），否则等于没写。TODO 只允许出现在后三段。

    4. 预算纪律（第 8 节冻结阀）

    • 入口 gzip ≥7KB：逐字节冻结，涨 1B 即构建失败。要么优化回去，要么走下面的显式更新流程。
    • 入口 gzip <7KB：按 5% 预警，超过即 warning（不阻断）。
    • 唯一合法的基线更新方式：
    node build.mjs --update-baseline   # 会重写 budget-baseline.json
git diff budget-baseline.json      # 必须逐行看过，确认每个 +N 都是有意为之

    禁止为了让构建通过而调大阈值函数、关闭冻结阀、或把入口改名绕过统计。已知 overlay 现为 7726B / 94.3%，是固定税 2398B 的主要承担者，任何"顺手加点样式"都应先算字节。

    5. 意图契约四段写法（摘要，全文见 docs/intent-template.md）

    1. 边界：负责 / 明确不负责（必须写承接方）。承接方写不出来的条目，说明是假边界。
    2. 状态机与失败态：状态 → 表达（data-*）→ 失败态落点，并写转移禁令（如"保存中不得接受 Esc"）。
    3. 可访问性：键盘键位表、焦点落点、非颜色编码、prefers-reduced-motion 降级。
    4. AI 选型提示：什么时候选它 / 什么时候别选（给出替代组件）/ 最小正确用法（可复制 HTML）/ 常见误用。

    写作口径：只写承诺，不写实现。"用了 flex 布局"、"内部有 3 层 div"不属于契约内容。

    6. 改动纪律

    • 一次只做一件事：不夹带无关的格式化、重命名、样式微调。审查看 diff 是否只有一个主题。
    • 先断言后修：修 bug 先补一条会失败的断言，再改代码；断言转 PASS 才算修完。
    • 不改历史断言来让结果变绿：确需调整的，在 commit message 里写明"原断言错在哪"。
    • 不删 docs/known-issues.md 的历史行：修完移到"已修复"表并保留一行。
    • 提交粒度：一个主题一个 commit；dist/ 永不入库；提交前必跑三条命令。
