    0. 口径更正带来的三个结论

    1. v1 的"3.3 分"高估了。 按通用库权重（组件广度、工程化、可访问性、国际化占主要权重），Cinder 通用层得分 2.6，Web Awesome 4.6，差距 2.0 分，属于"能用但还不是一个完整产品"的区间。
    2. 差距不在设计，在基础设施。 设计令牌、皮肤、密度、体积这些反而领先或持平；真正落后的是组件覆盖、类型、按需加载、i18n、文档与生态——通用库的"产品化"部分。
    3. ERP 定制不该作为豁免理由。 正确结构是：通用层补齐到"合格通用库"门槛（覆盖率 ≥85%、必备组件 0 缺失、20 项基础设施 ≥15 项达标），ERP 层继续做厚。两层分开考核，而不是用业务需求解释通用缺口。

    8. 三个架构决策需要重新评估（通用库视角）

    v1 把这三项当作"不必追"，在通用库定位下必须重新权衡。

    决策 现状 通用库视角的代价 建议
    不采用 Shadow DOM light DOM + 前缀 + @layer 宿主页面样式可能穿透；没有 ::part() 契约；主题边界靠约定 保留 light DOM（对 ERP 内嵌有利），但在文档明确"light DOM by design"，并补一条 lint 规则禁止无前缀选择器；若未来做 SaaS 多租户嵌入再评估
    单文件全量 CSS 23.2 KB 一次加载 只用 3 个组件的页面也要付全量；无法按需 必须改：按组件拆分，保留 cinder.css 全量入口；@layer 保证拆分后顺序不塌
    零依赖 无 Lit / 无 floating-ui 缺 form-associated、缺碰撞检测、缺跨框架类型 保留零依赖作为卖点；定位逻辑自研已够（Tour 已验证），表单用原生元素 + d.ts 补类型，不引入 Lit

    补充一条 v1 的判断修正："组件数量竞赛不该学"这句话不成立。对通用库，广度就是产品力；正确说法是"长尾不自研，用适配层 + 明确 roadmap"，而不是"不做"。

    9. 最终定位建议（修订）

    1. Cinder = 通用 UI 组件库 + ERP 增强层。base 层按通用库标准考核，erp 层按业务价值考核，两套指标分开看。
    2. 短期优先级：类型、按需加载、必备 14 组件、i18n/RTL、文档站。这五项决定"别人能不能用"，比再加 3 套皮肤重要。
    3. 中期差异化：把 6 个业务块 + 8 套皮肤 + 密度体系做成"开箱即用的 ERP 主题包"，这是 Web Awesome 永远不会有、而 Cinder 可以免费给的东西。
    4. 对外话术：不要自称"ERP 组件库"（会被当成业务框架），应称"面向后台与 ERP 场景的通用 UI 组件库"——先过通用库的及格线，再谈 ERP 加成。
